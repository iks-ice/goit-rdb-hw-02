Найскладнішим для мене виявилося забезпечення point-in-time correctness. Звичайна реляційна модель добре показує, як користувач пов’язаний із фільмом через оцінку, але для ML цього недостатньо: важливо знати, яке саме значення ознаки було доступне в момент прогнозу. Потрібно одночасно контролювати час прогнозування, інтервали чинності ознак і час появи цільової оцінки. Особливо показовим є тест на точній межі valid_to, де неправильна умова могла б повернути дві версії.

Головний архітектурний компроміс полягає в розділенні нормалізованої бізнесової моделі та денормалізованого feature store. Таблиці користувачів, фільмів, жанрів і зв’язків зберігають дані без зайвих повторів, а offline-рівень дозволяє відтворювати історію. Online-рівень навмисно містить готові агрегати в одному рядку. Це пришвидшує читання, але створює ризик застарілих значень. Я використав feature_ts та UPSERT, який не перезаписує новіші ознаки старішими.

За високого навантаження я б залишив online lookup за user_id і матеріалізував найбільш затребувані ознаки наперед. Для зменшення затримок можна використати кеш або key-value сховище, горизонтальне масштабування та метрики свіжості. При цьому джерелом істини для навчання залишилася б версіонована offline-історія, а не online-кеш. Також потрібні моніторинг розбіжностей між шарами та контроль затримки оновлення.

Протягом наступних шести місяців можливі зміни назв і типів ознак, нові визначення 30-денного вікна або видалення колонок. Це ризик для вже навчених моделей: та сама назва ознаки може почати означати інше. Я б запровадив версіонування feature definitions, сумісні міграції, перевірки контрактів схеми й підтримку старих версій до завершення переходу. Ця робота показала, що коректна схема для ML має забезпечувати не лише зручність SQL, а й відтворюваність прогнозів у часі.
